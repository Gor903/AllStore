# AllStore.am — План сборки MVP (инженерная версия)

Версия: 0.2
Дата: 2026-09-19
Статус: стек зафиксирован, план сборки для разработки

Этот документ дополняет `AllStore_plan.md` (продуктовый план) и фокусируется на том, **как** технически собирать MVP: архитектура, структура репозитория, стандарты качества, CI/CD и пошаговый план реализации под конкретный стек.

## 1. Зафиксированный стек

**Backend**
- Python 3.13+
- FastAPI
- SQLAlchemy 2.x (async)
- Pydantic v2
- Alembic
- pytest

**Frontend**
- Next.js (App Router)
- TypeScript (strict)
- Tailwind CSS

**База данных**
- PostgreSQL

**Инфраструктура**
- Docker Compose
- Nginx
- S3-compatible storage (MinIO локально, S3/аналог в проде)

**Тестирование**
- pytest (backend, unit + integration)

- Playwright (e2e, весь стек)

**CI/CD**
- GitHub Actions

Стек закрывает открытый вопрос №16 из продуктового плана ("Какой стек будет выбран?"). Остальные открытые вопросы (раздел 26 исходного плана) стек не решает — они по-прежнему требуют отдельных решений до начала соответствующих этапов.

## 2. Принципы "профессионально, без багов"

Раз цель — стабильность и качество, а не скорость любой ценой, фиксируем правила, которые действуют на всех этапах:

1. **Ничего не мержится без CI.** Зелёный pipeline — обязательное условие для merge в main.
2. **Типизация везде.** mypy strict на backend, TypeScript strict на frontend. Никаких `Any` / `any` без явного комментария-обоснования.
3. **Тесты — часть Definition of Done.** Новая бизнес-логика без тестов не считается завершённой (см. раздел 22 продуктового плана — это же касается и не-AI-разработки).
4. **Миграции — единственный способ менять схему БД.** Ручные ALTER в проде запрещены.
5. **Один источник правды для контрактов.** Pydantic-схемы backend → OpenAPI → генерация типов для frontend (не дублировать типы руками).
6. **Multi-tenant изоляция проверяется тестами, а не только код-ревью.** Для каждого ресурса, привязанного к `business_id`, должен быть тест "чужой tenant не видит и не может изменить".
7. **Секреты не в репозитории.** `.env` в `.gitignore`, пример — в `.env.example`.
8. **Маленькие PR.** Один PR — одна задача из плана (раздел 8 ниже), проще ревьюить и находить баги.

## 4. Backend: архитектурные правила

### 4.1. Слои и границы

- **api/** — только парсинг запроса, вызов сервиса, сериализация ответа. Никакой бизнес-логики.
- **services/** — вся бизнес-логика (например, "одобрить товар" = сменить статус + записать moderation_review + отправить уведомление). Не зависит от FastAPI.
- **repositories/** — единственное место, где пишутся SQL-запросы через SQLAlchemy. Каждый запрос к tenant-данным обязан фильтровать по `business_id`.
- **models/** — SQLAlchemy 2.x декларативные модели, с типизированными `Mapped[...]` аннотациями.
- **schemas/** — отдельные Pydantic-схемы для Create / Update / Read (не переиспользовать одну модель на всё).

### 4.2. Multi-tenant изоляция (backend)

- Единая база данных, общие таблицы с `business_id` (модель 1 из раздела 9.3 продуктового плана) — самая простая для старта.
- Dependency `get_current_business()` резолвит tenant из Host header на публичных маршрутах и из токена — в dashboard продавца.
- **Правило:** ни один repository-метод не принимает "все товары", если сущность привязана к бизнесу — только `get_products(business_id, ...)`.
- Отдельный набор интеграционных тестов: создать два бизнеса, проверить что API одного не отдаёт и не позволяет менять данные другого (403/404, не утечка данных с фильтрацией на фронте).

### 4.3. Обработка ошибок

- Единый формат ошибки в JSON: `{"error": {"code": "...", "message": "...", "details": [...]}}`.
- Глобальные exception handlers в FastAPI: `ValidationError`, `NotFoundError`, `PermissionDeniedError`, `ConflictError` (например, занятый субдомен) → HTTP-коды 422/404/403/409.
- Никаких "голых" 500 с трейсбеком наружу — логировать полностью, наружу отдавать безопасное сообщение.

### 4.4. Конфигурация

- Pydantic `BaseSettings` для конфигурации окружения (DB URL, S3-креды, secret keys), с валидацией при старте — приложение не должно запуститься с неполной конфигурацией.

## 5. Frontend: архитектурные правила

- **App Router**, три route-группы: `(public)` — витрина/каталог, `(dashboard)` — кабинет продавца, `(admin)` — админка. Разные layout, разная авторизация.
- Публичные страницы (каталог, страница товара, страница магазина) — server-side рендеринг/статическая генерация ради SEO (раздел 20 продуктового плана).
- Кабинет продавца и админка — обычный CSR, SEO не важен.
- Типы для API-клиента генерируются из OpenAPI-схемы backend (`openapi-typescript` или аналог) — исключает рассинхрон типов между frontend и backend.
- Tailwind: зафиксировать design tokens (цвета, отступы, типографика) в `tailwind.config` — это и есть "общий UI-скелет с ограниченной кастомизацией" из принципов продукта.
- Определение магазина по субдомену — через middleware Next.js (`middleware.ts`), читает `Host`, прокидывает `subdomain` в контекст рендеринга.

## 6. База данных и миграции

- Каждое изменение схемы — через Alembic-миграцию, с ревью в PR (сгенерированную миграцию нельзя мержить не глядя).
- Каждая миграция должна быть обратимой (`downgrade()` реализован, не `pass`).
- Индексы обязательны на: `stores.subdomain` (unique), `products.business_id`, `products.moderation_status`, `products.publication_status`, `businesses.owner_user_id`.
- CI прогоняет `alembic upgrade head` на чистой БД как часть тестов — миграции, которые не применяются, ломают pipeline.
- Резервное копирование БД настраивается уже на этапе 1 (инфраструктура), не откладывается до продакшена.

## 7. Инфраструктура

### 7.1. Docker Compose (локальная разработка)

Сервисы: `backend`, `frontend`, `postgres`, `nginx`, `minio` (S3-совместимое хранилище для локальной разработки), опционально `redis` (когда понадобится, не в MVP).

### 7.2. Nginx

- Reverse proxy, маршрутизация по Host header: `*.allstore.am` → frontend/backend в зависимости от пути.
- Валидация Host header на backend-уровне тоже (защита от подмены — раздел 19 продуктового плана).
- В проде — TLS-терминация (wildcard-сертификат для `*.allstore.am`).

### 7.3. Хранение файлов

- Все загрузки (логотипы, баннеры, фото товаров) — сразу через S3-совместимый клиент, даже локально (MinIO), чтобы не переписывать логику загрузки при переходе в прод.
- Ограничение типа и размера файла — на backend, не полагаться на frontend-валидацию.

## 8. CI/CD (GitHub Actions)

### 8.1. `backend-ci.yml`
На каждый PR и push в main:
1. Установка зависимостей (кэш).
2. `ruff` (lint) + `ruff format --check`.
3. `mypy` (типы).
4. Поднять тестовый PostgreSQL (service container).
5. `alembic upgrade head`.
6. `pytest` с покрытием, минимальный порог покрытия для новых файлов.

### 8.2. `frontend-ci.yml`
1. `npm ci`.
2. ESLint + Prettier check.
3. `tsc --noEmit` (проверка типов).
4. `vitest run`.
5. `next build` (проверка, что билд не ломается).

### 8.3. `e2e.yml`
1. Поднять весь стек через `docker-compose`.
2. `playwright test` — ключевые сценарии (регистрация продавца, создание магазина, добавление товара, модерация, отображение в каталоге).
3. Запускать на PR в основные ветки и/или по расписанию — решить исходя из времени выполнения.

### 8.4. `deploy-staging.yml`
- Триггер: merge в main.
- Сборка Docker-образов, пуш в registry, деплой на staging.
- Прод-деплой — отдельный workflow с ручным подтверждением (не автоматический на этом этапе).

## 9. Определение готовности (Definition of Done) для задачи

Задача (любая, включая задачи для AI-агентов из раздела 22 продуктового плана) считается завершённой, если:

- Код проходит lint и типизацию.
- Есть тесты на новую логику, включая tenant-изоляцию, если применимо.
- CI зелёный.
- Миграции (если есть) обратимы и применены в CI.
- Ошибки обрабатываются по единому формату (раздел 4.3).
- Нет секретов и захардкоженных значений окружения в коде.
- PR описывает: что сделано, что затронуто, как протестировано.

## 10. Пошаговый план реализации (стек-специфичный)

Соответствует этапам 0–9 из продуктового плана, но с конкретными техническими задачами.

**Пересмотрено 2026-09-21.** Этапы 1–6 закрыты. При этом выяснилось, что девять этапов не покрывают MVP, описанный в самом продуктовом плане: панель продавца (раздел 7.3), административная панель (7.4), контакты и социальные ссылки продавца, оформление магазина, восстановление доступа в интерфейсе, жалобы и управление категориями в разбивку не попали. Этапы 10–15 ниже закрывают этот разрыв. Нумерация идёт по порядку планирования, а не по порядку исполнения — фактический порядок работ виден в журнале `AllStore_acceptance_criteria.md`.

### Этап 1 — инфраструктура
- Инициализировать монорепозиторий по структуре из раздела 3.
- `docker-compose.dev.yml`: backend, frontend, postgres, minio, nginx.
- Настроить `ruff`, `mypy`, `pre-commit` (backend); ESLint, Prettier, `tsconfig` strict (frontend).
- Настроить Alembic (base revision).
- `backend-ci.yml`, `frontend-ci.yml` — минимальные версии (lint + typecheck), тесты добавятся по мере кода.
- **DoD:** `docker compose up` поднимает пустой backend (health-check endpoint) и frontend (стартовая страница), CI зелёный на пустом проекте.

### Этап 2 — пользователи и роли
- Модели `users` (+ роли enum: guest не хранится, buyer/seller/moderator/admin).
- Регистрация, вход, хеширование паролей (passlib/bcrypt или аналог), JWT или session-based — зафиксировать выбор в ADR.
- FastAPI dependencies: `get_current_user`, `require_role(...)`.
- Frontend: страницы регистрации/входа, хранение токена, защищённые роуты в `(dashboard)` и `(admin)`.
- Тесты: unit на сервисы auth, integration на роуты (в т.ч. попытка доступа без нужной роли → 403).

### Этап 3 — магазины и субдомены
- Модели `businesses`, `stores`.
- Проверка уникальности субдомена (unique constraint + человекочитаемая ошибка 409 при конфликте).
- Резолв магазина по Host header (backend middleware/dependency + Next.js middleware).
- Список зарезервированных субдоменов (www, api, admin, dashboard и т.д.) — вынести в конфиг, не в код.
- Тесты: создание магазина, конфликт субдоменов, резолв несуществующего субдомена → 404.

### Этап 4 — товары
- Модели `products`, `product_images`, `categories`.
- CRUD с обязательной проверкой `business_id` владельца на каждом мутирующем эндпоинте.
- Загрузка фото → S3-совместимое хранилище, валидация типа/размера.
- Тесты: tenant-изоляция (продавец A не может редактировать товар продавца B), валидация полей.

### Этап 5 — модерация
- Модель `moderation_reviews`, статус-машина товара (pending → approved/rejected → published/hidden).
- Очередь на проверку для роли moderator, endpoint approve/reject с причиной.
- Уведомление продавцу о результате (простой email на этом этапе, см. этап 8 продуктового плана).
- Тесты: полный цикл статус-машины, попытка публикации без одобрения → запрещена.

### Этап 6 — общий каталог
- Публичные эндпоинты: список товаров/магазинов, поиск, фильтры по категориям — только `publication_status = published` и магазин не заблокирован.
- SSR/SSG страницы каталога, магазина, товара на frontend.
- SEO: meta, sitemap.xml, robots.txt, canonical, Open Graph.
- Тесты: непубликуемые/заблокированные товары не должны быть доступны даже по прямой ссылке.

### Этап 7 — главная страница и продвижение
- Блоки "новые товары/магазины", подборки — без сложной логики продвижения на этом этапе.

### Этап 8 — уведомления
- Email-интеграция (провайдер выбрать отдельно — открытый вопрос продуктового плана), базовые триггеры уведомлений.

### Этап 9 — тестирование с реальными продавцами
- Стабилизация, фикс критичных багов, без новых фич в этом этапе.

### Этап 10 — кабинеты продавца и модератора *(сделано вне очереди, 2026-09-21)*
- Панель продавца: магазин, список товаров со статусами, карточка товара с фотографиями и действиями.
- Очередь модератора: товары и заявки продавцов, решения с обязательной причиной.
- Сделано раньше срока, потому что до этого наполнять сайт можно было только запросами к API.

### Этап 11 — оформление магазина и контакты продавца
- Эндпоинты правки магазина и бизнеса: описание, логотип, баннер, основной и дополнительный цвет, тема.
- Загрузка логотипа и баннера в то же хранилище, что и фото товаров, с той же проверкой типа и размера.
- Контактные данные продавца (телефон, мессенджеры, способ связи) и социальные ссылки — таблица `social_links` из раздела 10 продуктового плана.
- Показ контактов покупателю на странице товара и на витрине. Без этого фраза «свяжитесь с продавцом напрямую» ничем не подкреплена, а других способов заказа в MVP нет.
- Экран настроек магазина в кабинете продавца.
- **DoD:** продавец задаёт оформление и контакты мышью, покупатель видит их на витрине и в карточке товара.

### Этап 12 — восстановление доступа и подтверждение email
- Экраны «забыли пароль» и «новый пароль» поверх эндпоинтов, готовых с этапа 2.
- Отправка письма со ссылкой — зависит от этапа 8 (провайдер email).
- Подтверждение email: поле `email_verified_at` заведено на этапе 2 и до сих пор не используется.
- **DoD:** продавец, забывший пароль, возвращает доступ сам, без обращения в поддержку.

### Этап 13 — административная панель
- Список пользователей с поиском, смена роли (в том числе назначение модератора) — сейчас роль ставится только прямой записью в базу.
- Блокировка и разблокировка аккаунта покупателя.
- Управление категориями: создание, переименование, скрытие.
- Скрытие и возврат на полку уже опубликованного товара — в API есть с этапа 5, экрана нет.
- Журнал административных действий (`audit_logs` из раздела 10 продуктового плана).
- **DoD:** ни одно административное действие не требует доступа к базе.

### Этап 14 — жалобы
- Таблица `reports` из раздела 10 продуктового плана.
- Кнопка «пожаловаться» на товаре и на магазине для покупателя и гостя.
- Очередь жалоб у модератора, связка с существующими решениями (скрыть товар, приостановить магазин).
- **DoD:** жалоба доходит до модератора и закрывается решением с причиной.

### Этап 15 — эксплуатация и релиз
- Сервер, домен, wildcard DNS `*.allstore.am`, wildcard TLS через DNS-01.
- `deploy-staging.yml` и `e2e.yml` — оба описаны в разделе 8 и до сих пор не существуют.
- Playwright: сквозной сценарий «регистрация продавца → магазин → товар → модерация → каталог».
- Резервное копирование PostgreSQL и объектного хранилища, проверка восстановления.
- Сбор логов и ошибок, базовый мониторинг доступности.
- **DoD:** сайт доступен по настоящему адресу, ссылку можно отправить человеку, а падение видно раньше, чем о нём сообщит продавец.

## 11. Что решить отдельно (ADR) до соответствующего этапа

Технические решения, которые должны быть зафиксированы как Architecture Decision Records, а не решаться "по ходу":
