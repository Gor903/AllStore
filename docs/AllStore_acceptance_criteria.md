## Как пользоваться этим файлом

Этот файл — чек-лист приёмки для каждой задачи MVP плюс журнал того, что уже сделано.

**Порядок работы для агента (или разработчика):**

1. Перед началом задачи — найти её в списке ниже, прочитать Acceptance Criteria (AC) полностью.
2. Сделать задачу.
3. Проверить каждый пункт AC самостоятельно (запустить тесты, проверить вручную, где нужно).
4. Если **все** пункты AC выполнены — отметить задачу как `[x]` в списке ниже.
5. Добавить запись в раздел "Журнал выполнения" в конце файла, по шаблону из раздела "Формат записи журнала".
6. Если хотя бы один пункт AC не выполнен — задача остаётся `[ ]`, в журнал ничего не пишется, вместо этого агент сообщает, что именно не выполнено и почему.

Задача считается закрытой только тогда, когда отмечена `[x]` **и** есть соответствующая запись в журнале. Одно без другого не считается.

Общие критерии из `AllStore_build_plan.md` (раздел 9, Definition of Done) действуют для КАЖДОЙ задачи дополнительно к AC ниже: код проходит lint/типизацию, CI зелёный, нет секретов в коде, PR описан.

### [Этап 1 / Задача 1.2] — Docker Compose (dev)
Дата: 2026-09-19
Исполнитель: Claude Opus 5 (агент)

Что сделано:
- Локальный стек из пяти сервисов: `postgres`, `minio`, `backend`, `frontend`, `nginx`.
- Backend отдаёт `/health` и `/health/ready`, при старте применяет миграции и создаёт bucket в MinIO.
- Frontend отдаёт стартовую страницу через nginx и показывает состояние backend.

Как сделано (файлы, подход, ключевые решения):
- `infra/docker-compose.dev.yml` — сервисы, healthcheck'и (`pg_isready`, `mc ready local`, HTTP-проверка backend), `depends_on: service_healthy` для backend, именованные volume под данные Postgres, MinIO, `node_modules` и кэш Next.
- `compose.yaml` в корне подключает dev-файл через `include`, чтобы `docker compose up` работал из корня репозитория без флагов.
- Значения окружения заданы в compose через `${VAR:-дефолт}`, поэтому стек поднимается без предварительной настройки; `.env` в корне (gitignored) переопределяет порты и учётные данные. `DATABASE_URL` собирается из `POSTGRES_*`, ключи S3 — из `MINIO_ROOT_*`, так что рассинхрона между сервисами быть не может.
- `infra/nginx/conf.d/allstore.conf` — reverse proxy: `/api/`, `/health`, `/docs`, `/openapi.json` → backend, остальное → frontend, с пробросом `Host` (нужен для резолва магазина по субдомену на этапе 3) и websocket-заголовками под HMR.
- `backend/Dockerfile` и `frontend/Dockerfile` — многостадийные, с раздельными целями `dev` и `prod` (uv-venv в `/opt/venv`, non-root пользователь и `output: standalone` для прод-образа frontend).
- Разделены серверный и браузерный API-URL (`INTERNAL_API_URL` / `NEXT_PUBLIC_API_URL`): SSR ходит в backend по внутренней сети, браузер — через nginx.

Как проверено:
- `docker compose up --build -d` на чистых volume: все контейнеры поднялись, postgres и minio — `healthy`.
- `curl http://localhost:8081/health` → `200 {"status":"ok","env":"local"}`; `/health/ready` → `{"status":"ok","database":true,"storage":true}`.
- Postgres из backend-контейнера: подключение по `DATABASE_URL` из окружения контейнера, `show server_version` → 17.11, `select version_num from alembic_version` → `0001`.
- MinIO: в логах старта `app.core.storage: created bucket allstore-dev`, `list_buckets()` из backend-контейнера возвращает `['allstore-dev']`.
- Стартовая страница проверена реальным Chrome (Playwright, headless выключен): `http status 200`, `title: AllStore.am`, бейдж `Backend: доступен`, в консоли 0 ошибок и предупреждений (были только info про React DevTools и `[HMR] connected`).
- Ошибочный маршрут отдаёт единый формат ошибки: `{"error":{"code":"not_found",...}}`.

Отклонения от плана (если есть):
- Образ MinIO взят с `quay.io/minio/minio` — на Docker Hub `minio/minio` отдаёт `pull access denied`.
- На этой машине занят порт 8080, поэтому проверка выполнялась с `HTTP_PORT=8081` из корневого `.env`; дефолт в compose остался 8080.
- В первой проверке консоль браузера показывала 404 на `/favicon.ico` — добавлен `frontend/src/app/icon.svg`, после чего консоль чистая.

- Реальный Chrome против поднятого стека: регистрация продавца уводит на `/dashboard`, там видны «Магазин Поток» и «ИП "Поток" — на проверке модератором»; выход возвращает на `/login`; вход с неверным паролем показывает «Неверный email или пароль»; вход с верным — снова кабинет.
- `localStorage` и `sessionStorage` после входа пустые, скриптам доступна только CSRF-cookie: `allstore_csrf=…`. Токены доступа и обновления httpOnly.
- Через nginx: `/dashboard` и `/admin` без сессии дают 307 на `/login?next=…`, `/login` и `/register` отдают 200.
- 17 тестов Vitest: разбор конверта ошибок, редиректы proxy, показ ошибки входа, поля продавца, отправка CSRF-заголовка, пустой телефон не уходит в запрос.
- `npm run lint`, `format:check`, `typecheck` на чистом `.next`, `next build` — зелёные.

Отклонения от плана (если есть):
- Playwright в зависимости проекта не добавлялся: сквозные сценарии относятся к этапу 9. Браузерная проверка выполнена внешним Playwright из временного каталога.
- Проверка «ошибка показывается пользователю» сначала дала ложный отрицательный результат: селектор `role=alert` попал в служебный route announcer самого Next, который пуст. Форма работала корректно — это была ошибка проверки, а не кода.
