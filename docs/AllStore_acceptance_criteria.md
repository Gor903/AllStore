## Как пользоваться этим файлом

Этот файл — чек-лист приёмки для каждой задачи MVP плюс журнал того, что уже сделано.

**Порядок работы для агента (или разработчика):**

1. Перед началом задачи — найти её в списке ниже, прочитать Acceptance Criteria (AC) полностью.
2. Сделать задачу.
3. Проверить каждый пункт AC самостоятельно (запустить тесты, проверить вручную, где нужно).
4. Если **все** пункты AC выполнены — отметить задачу как `[x]` в списке ниже.
5. Добавить запись в раздел "Журнал выполнения" в конце файла, по шаблону из раздела "Формат записи журнала".
6. Если хотя бы один пункт AC не выполнен — задача остаётся `[ ]`, в журнал ничего не пишется, вместо этого агент сообщает, что именно не выполнено и почему.

Задача считается закрытой только тогда, когда отмечена `[x]` **и** есть соответствующая запись в журнале. Одно без другого не считается.

Общие критерии из `AllStore_build_plan.md` (раздел 9, Definition of Done) действуют для КАЖДОЙ задачи дополнительно к AC ниже: код проходит lint/типизацию, CI зелёный, нет секретов в коде, PR описан.

### [Этап 1 / Задача 1.2] — Docker Compose (dev)
Дата: 2026-09-19
Исполнитель: Claude Opus 5 (агент)

Что сделано:
- Локальный стек из пяти сервисов: `postgres`, `minio`, `backend`, `frontend`, `nginx`.
- Backend отдаёт `/health` и `/health/ready`, при старте применяет миграции и создаёт bucket в MinIO.
- Frontend отдаёт стартовую страницу через nginx и показывает состояние backend.

Как сделано (файлы, подход, ключевые решения):
- `infra/docker-compose.dev.yml` — сервисы, healthcheck'и (`pg_isready`, `mc ready local`, HTTP-проверка backend), `depends_on: service_healthy` для backend, именованные volume под данные Postgres, MinIO, `node_modules` и кэш Next.
- `compose.yaml` в корне подключает dev-файл через `include`, чтобы `docker compose up` работал из корня репозитория без флагов.
- Значения окружения заданы в compose через `${VAR:-дефолт}`, поэтому стек поднимается без предварительной настройки; `.env` в корне (gitignored) переопределяет порты и учётные данные. `DATABASE_URL` собирается из `POSTGRES_*`, ключи S3 — из `MINIO_ROOT_*`, так что рассинхрона между сервисами быть не может.
- `infra/nginx/conf.d/allstore.conf` — reverse proxy: `/api/`, `/health`, `/docs`, `/openapi.json` → backend, остальное → frontend, с пробросом `Host` (нужен для резолва магазина по субдомену на этапе 3) и websocket-заголовками под HMR.
- `backend/Dockerfile` и `frontend/Dockerfile` — многостадийные, с раздельными целями `dev` и `prod` (uv-venv в `/opt/venv`, non-root пользователь и `output: standalone` для прод-образа frontend).
- Разделены серверный и браузерный API-URL (`INTERNAL_API_URL` / `NEXT_PUBLIC_API_URL`): SSR ходит в backend по внутренней сети, браузер — через nginx.

Как проверено:
- `docker compose up --build -d` на чистых volume: все контейнеры поднялись, postgres и minio — `healthy`.
- `curl http://localhost:8081/health` → `200 {"status":"ok","env":"local"}`; `/health/ready` → `{"status":"ok","database":true,"storage":true}`.
- Postgres из backend-контейнера: подключение по `DATABASE_URL` из окружения контейнера, `show server_version` → 17.11, `select version_num from alembic_version` → `0001`.
- MinIO: в логах старта `app.core.storage: created bucket allstore-dev`, `list_buckets()` из backend-контейнера возвращает `['allstore-dev']`.
- Стартовая страница проверена реальным Chrome (Playwright, headless выключен): `http status 200`, `title: AllStore.am`, бейдж `Backend: доступен`, в консоли 0 ошибок и предупреждений (были только info про React DevTools и `[HMR] connected`).
- Ошибочный маршрут отдаёт единый формат ошибки: `{"error":{"code":"not_found",...}}`.

Отклонения от плана (если есть):
- Образ MinIO взят с `quay.io/minio/minio` — на Docker Hub `minio/minio` отдаёт `pull access denied`.
- На этой машине занят порт 8080, поэтому проверка выполнялась с `HTTP_PORT=8081` из корневого `.env`; дефолт в compose остался 8080.
- В первой проверке консоль браузера показывала 404 на `/favicon.ico` — добавлен `frontend/src/app/icon.svg`, после чего консоль чистая.

Исполнитель: Claude Opus 5 (агент)

Что сделано:
- `POST /api/v1/products`, `GET /api/v1/products`, `GET|PATCH|DELETE /api/v1/products/{id}` — продавец заводит, читает, правит и архивирует товары только своего бизнеса.
- Чужой товар отвечает 404 на чтение, правку и архивацию; данные при этом не меняются.
- Новый товар создаётся `pending` + `draft` — публично невидим.
- Обязательные поля (название, цена, категория) проверяются на backend.

Как сделано (файлы, подход, ключевые решения):
- `app/deps/business.py::get_current_business` — tenant dashboard-запроса резолвится из сессии, а не из Host. Каждый запрос к товарам фильтруется по этому бизнесу, поэтому ни подменённый заголовок, ни угаданный id в пути к чужим данным не ведут.
- `app/repositories/products.py` — `get_owned(session, business_id, product_id)`: товар ищется по владельцу и id вместе, никогда по одному id. Правило из раздела 4.2 плана сборки выполняется самой сигнатурой, а не дисциплиной вызывающего.
- Чужой товар отвечает 404, а не 403: 403 подтвердил бы, что такой товар существует. AC допускает оба кода.
- `app/services/products.py::update_product` — PATCH меняет только пришедшие поля (`exclude_unset`). Правка того, что судил модератор (название, описание, категория), возвращает товар в очередь: `approved` → `pending`, публикация → `draft`. Цена и остаток вердикт не сбрасывают — переоценка не повод пересматривать карточку.
- Удаление сделано архивацией (`products.archived_at`, миграция 0005): строка остаётся, поэтому у фото, будущего вердикта модератора и будущих строк заказа сохраняется объект, на который они ссылаются. Архивный товар исчезает из списка продавца и отвечает 404 на чтение и правку; заодно ему проставляется `publication_status = hidden`, чтобы он не всплыл даже в запросе, который забудет про `archived_at`.
- Частичный индекс `ix_products_business_id_live` под ровно тот запрос, которым кабинет читает живые товары одного бизнеса.
- `ProductUpdateRequest` запрещает лишние поля (`extra="forbid"`) и `null` во всём, кроме описания: `{"name": null}` — это ошибка клиента, а не намерение очистить название. Проверка — `model_validator`, ответ 422.
- Ни `moderation_status`, ни `publication_status` в схемах запроса не значатся: продавец не должен одобрять и публиковать сам себя. Переходы появятся с модерацией (этап 5).
- Валюта наружу не выставлена и остаётся `AMD`: мультивалютный каталог без правил сравнения цен хуже, чем его отсутствие. Колонка из раздела 10 плана на месте и ждёт своего этапа.
- Пагинация `limit` (1..100, по умолчанию 20) и `offset`; сортировка по `created_at desc`, id разбивает ничью — два товара одной миллисекунды не должны прыгать между страницами.

Как проверено:

- Тестами закрыто: создание и дефолты, тримминг названия, три отсутствующих обязательных поля, восемь битых значений (пустое название, 256 символов, отрицательная цена, три знака после запятой, не-число, отрицательный остаток, несуществующий статус наличия, не-uuid), неизвестная и скрытая категория, попытка задать `moderation_status`, `publication_status` и `business_id`, покупатель, аноним, продавец без бизнеса, список только своих товаров, пагинация и три битых её варианта, чтение своего и чужого товара, правка своего и чужого, перенос в другую категорию и в несуществующую, `null` в неочищаемом поле, очистка описания, сброс модерации при правке названия и его сохранение при правке цены, архивация, невидимость и неправимость архивного, архивация чужого, три мутации без CSRF.

Отклонения от плана (если есть):

- Правка одобренного товара сбрасывает модерацию — в AC 4.2 этого нет, но без правила продавец получал бы одобрение на одну карточку и подменял её другой.

### [Этап 4 / Задача 4.3] — Загрузка фото
Дата: 2026-09-21
Исполнитель: Claude Opus 5 (агент)

Что сделано:
- `POST /api/v1/products/{id}/images` кладёт файл в S3-совместимое хранилище и заводит строку галереи; `DELETE /api/v1/products/{id}/images/{image_id}` убирает и строку, и объект.
- Тип проверяется по сигнатуре файла, размер — по настройке `MAX_UPLOAD_SIZE_MB` (по умолчанию 5 МБ).
- Недопустимый файл отвечает 422 с понятным текстом, слишком большой — 413; 500 нет ни там, ни там.
- Галерея приезжает вместе с товаром: `ProductRead.images`.

Как сделано (файлы, подход, ключевые решения):
- `app/core/images.py::detect_image_format` читает формат из самих байтов. `Content-Type` multipart-части пишет клиент — это заявление отправителя, а не факт. Переименованный в `.jpg` исполняемый файл сюда не проходит, а SVG, который вообще документ со скриптами, не имеет сигнатуры и отсекается вместе со всем остальным. Принимаются jpeg, png, gif, webp.
- `app/services/product_images.py::read_within_limit` читает не больше `limit + 1` байта: одного лишнего байта достаточно, чтобы отказать, остальное в память не тянется. `client_max_body_size 10m` в nginx уже стоял и остаётся внешней границей — приложение отвечает 413 раньше.
- Строка заводится до заливки: упавшая заливка откатывает транзакцию и не оставляет следов, обратный порядок бросил бы объект в бакете без владельца. Ключ генерируем мы, поэтому URL известен до `put_object`.
- Ключ лежит под префиксом арендатора — `products/{business_id}/{product_id}/{uuid}.{ext}`, расширение берётся из сигнатуры, а не из имени, присланного клиентом.
- Удаление наоборот: сначала строка и коммит, потом объект. Объект без строки стоит места, строка без объекта показывает покупателю битую картинку. Ошибка удаления объекта логируется и не роняет запрос, который уже прошёл.
- `app/core/storage.py::_ensure_public_read` выдаёт бакету политику анонимного `s3:GetObject` при старте. Уже существующая политика не трогается: её автор знал, зачем бакет, и CDN перед ним может требовать что-то уже.
- Потолок в 10 фото на товар (`image_limit_reached`, 409) — в AC нет, но без него один товар может занять весь бакет.

Как проверено:
- `uv run pytest` — 282 passed; 49 новых тестов. Покрытие `app/core/images.py`, `app/repositories/product_images.py`, `app/services/product_images.py` — 100%, `app/core/storage.py` — 85% (непокрытое было непокрыто и раньше), общее 97%.
- Тестами закрыто: четыре поддерживаемых формата и то, что расширение идёт от байтов, а не от имени файла; PDF, исполняемый файл, SVG и пустой файл; превышение лимита размера; отсутствие и строки, и объекта после отказа; порядок в галерее; потолок в 10 фото; чужой и архивный товар; покупатель; запрос без CSRF; удаление строки и объекта; неизвестное фото; чужое фото; политика на свежем бакете и сохранность чужой политики; сборка и разбор публичного URL; проглоченная ошибка удаления.
- S3-путь в тестах идёт через moto: реальный boto3-клиент против S3 в том же процессе, инфраструктура для этого не нужна. moto перехватывает по endpoint, поэтому в тестах бакет адресуется как AWS, а не как MinIO из dev-стека; весь код выше этой границы — тот же, что в проде.
- Живой стек через nginx и MinIO: настоящий JPEG — 201, объект лежит в бакете, анонимный GET отдаёт 200 `image/jpeg` 2010 байт; PDF, переименованный в `.jpg`, — 422 `unsupported_image_type`; 6 МБ — 413 `image_too_large`; удаление — 204, после него объект отвечает 404, а товар остаётся без этого фото.
- Весь `backend-ci` через `act`: 10 шагов зелёные, `diff-cover` на изменённых строках выше порога.

Отклонения от плана (если есть):
- **Найдена и починена дыра на живой проверке.** Залитый файл отдавался анонимно с 403 — у бакета MinIO по умолчанию нет политики чтения, то есть покупатель увидел бы вместо фото ничего. Политика теперь выдаётся при старте, проверено анонимным `curl` до и после.
- Потолок в 10 фото и ограничение `alt_text` 255 символами в AC не значатся — добавлены как необходимый минимум вокруг загрузки.
- Порядок фото задаётся автоматически (новое уходит в конец), ручной пересортировки нет: в AC её нет, а витрине этапа 6 хватит обложки.

### [Этап 5 / Задача 5.1] — Модель данных модерации
Дата: 2026-09-21
Исполнитель: Claude Opus 5 (агент)

Что сделано:
- Таблица `moderation_reviews` создана миграцией 0006.
- Статус-машина товара собрана в одном модуле: `approve`, `reject`, `hide`, `publish`, `submit_for_review`, `withdraw`.
- Невозможные переходы отвечают 409 `invalid_transition` на уровне сервиса; публикация без одобрения запрещена.

Как сделано (файлы, подход, ключевые решения):
- `app/models/moderation.py` — запись вердикта: товар, модератор, решение (approved / rejected / hidden), причина, время. Таблица append-only: вердикт не правят, за ним пишут следующий, поэтому у неё `created_at` и нет `updated_at`, в отличие от остальных таблиц.
- Причина обязательна для отказа и проверяется в базе: `decision <> 'rejected' OR (reason IS NOT NULL AND reason ~ '\S')`. Регулярное выражение, а не `length(btrim(...))`: `btrim` по умолчанию снимает только пробелы, и строка из одного перевода строки сходила за причину — поймано тестом.
- `moderator_id` уходит в NULL при удалении аккаунта (`ON DELETE SET NULL`): модератор может уйти, запись о том, что он решил, — нет.
- `app/services/moderation.py` — единственное место, где меняются `moderation_status` и `publication_status`. Машина описана операциями, а не таблицей переходов: у каждой операции своя предпосылка и свой текст отказа, и читается она как список того, что модератор реально делает.
- Ключевое правило вынесено в отдельную проверку: `publish` требует `moderation_status = approved`, поэтому в `published` нельзя попасть иначе как через одобрение.
- Одобрение сразу ставит товар на полку (AC 5.2): ждать больше нечего, а отдельный шаг «одобрено, но не опубликовано» ничего не добавляет.
- Вердикт выносится один раз: повторный `approve` или `reject` отвечает 409, потому что иначе решение затиралось бы вместо того, чтобы за ним следовало новое.
- `products.update_product` и `products.archive_product` переведены на эту машину — прямых присваиваний статусов в сервисе товаров больше нет.
- Архивация (`withdraw`) снимает товар с полки, но вердикт не трогает: это действие продавца, а не решение модератора.

Как проверено:
- `uv run pytest` — 309 passed; 27 новых тестов. Покрытие `app/models/moderation.py` и `app/services/moderation.py` — 100%, общее 97%.
- Тестами закрыто: одобрение и отклонение, повторный вердикт (409), скрытие только опубликованного, возврат скрытого на полку, публикация без одобрения при трёх исходных статусах, повторная отправка из трёх состояний, повторная отправка того, что уже в очереди, архивация при любом вердикте, код и текст ошибки перехода; в базе — отказ без причины, причина из одних пробелов, одобрение и скрытие без причины, переживание истории после удаления модератора, порядок вердиктов, каскад при удалении товара.
- `alembic upgrade head` → `downgrade 0005` → `upgrade head` проходит начисто.
- `ruff check`, `ruff format --check`, `mypy` — чисто. Типы фронтенда пересобраны, диффа нет: эндпоинтов PR не добавляет.
- Весь `backend-ci` через `act`: 10 шагов зелёные, `diff-cover` на изменённых строках выше порога.

Отклонения от плана (если есть):
- У `moderation_reviews` нет `updated_at`, хотя он есть у всех остальных таблиц, — см. выше про append-only.
