# AllStore.am — План разработки платформы

Версия: 0.1  
Дата: 2026-09-19  
Статус: концепция и планирование MVP

---

## 1. Краткое описание проекта

AllStore.am — это платформа для зарегистрированных предпринимателей и небольших бизнесов в Армении.

Платформа предоставляет продавцам:

- Отдельную онлайн-витрину под субдоменом AllStore.
- Возможность добавлять и управлять физическими товарами.
- Представление магазина и товаров в общем каталоге AllStore.
- Дополнительное продвижение через социальные аккаунты AllStore.
- В будущем — онлайн-оплату, заказы, мобильные приложения и AI-ассистента.

Пример:

- allstore.am — главная страница платформы.
- cups.allstore.am — витрина магазина керамических чаш.
- models.allstore.am — витрина магазина изделий с 3D-принтера.

Все магазины используют общую техническую платформу, общий скелет интерфейса и общую инфраструктуру.

## 2. Основная ценность продукта

AllStore не обязательно заменяет Instagram или другие каналы продаж. Он создаёт ещё одно место, где продавец может представить свой товар.

Ценность для продавца:

1. Дополнительная онлайн-витрина.
2. Собственный адрес на домене AllStore.
3. Присутствие в общем каталоге.
4. Возможность продвижения через социальные аккаунты AllStore.
5. Единый и профессиональный шаблон магазина.
6. Возможность расширения магазина без самостоятельной разработки сайта.
7. Потенциальное подключение онлайн-оплаты и заказов.
8. Дополнительная видимость через поиск и AI-ассистента.

Ценность для покупателя:

1. Поиск товаров разных продавцов в одном месте.
2. Просмотр отдельных магазинов.
3. Фильтрация товаров.
4. Возможность находить товары через AI-ассистента.
5. Получение информации о продавце и товаре.
6. В будущем — заказ и оплата через платформу.

- Небольшие магазины.

- Каталог локальных авторов.
- Витрина начинающих продавцов.

- Сектор с ограниченными возможностями.
- Сектор, где действуют отдельные правила проверки.

Важно: не смешивать требования к зарегистрированным предпринимателям и неформальным продавцам без чётких правил.

Первый рынок:

- Армения.
- Валюта: AMD.
- Основные языки: определить на этапе требований.

## 6. MVP — минимальная первая версия

### 6.1. Цель MVP

Создать работающую платформу, которую можно протестировать на первых реальных продавцах.

Цель MVP — не реализовать все функции, а проверить:

- Готовы ли продавцы регистрироваться.
- Удобно ли добавлять товары.
- Понятно ли покупателям, как находить товары.
- Работает ли система субдоменов.
- Удобно ли модерировать товары.
- Нужен ли общий каталог.
- Какие функции продавцы считают ценными.

### 6.2. Функции MVP

#### Публичная часть

- Главная страница AllStore.
- Список магазинов.
- Список товаров.
- Поиск по товарам.
- Фильтр по категориям.
- Страница отдельного магазина.
- Страница отдельного товара.
- Информация о продавце.
- Контактная информация.
- Ссылки на внешние социальные аккаунты продавца.

#### Регистрация и авторизация

- Регистрация покупателя.
- Регистрация продавца.
- Вход и выход.
- Восстановление доступа.
- Разделение ролей.
- Подтверждение email или телефона — выбрать после исследования.
  **Решено 2026-09-19:** логин — email (обязателен и уникален), телефон опционален; поле подтверждения email закладывается на этапе 2, но вход не блокирует.

#### Магазин продавца

- Название магазина.
- Описание.
- Логотип.
- Обложка или баннер.
- Контактные данные.
- Социальные ссылки.
- Выбор субдомена.
- Изменение цветовой темы.
- Статус магазина: pending, active, suspended, blocked.

#### Управление товарами

- Добавление товара.
- Редактирование товара.
- Удаление или архивирование товара.
- Загрузка фотографий.
- Название.
- Описание.
- Цена в AMD.
- Категория.
- Количество или статус наличия.
- Статус модерации.
- Статус публикации.

#### Модерация

- Товар после создания получает статус pending.
- Модератор проверяет товар.
- После одобрения товар становится публичным.
- Отклонённый товар получает причину отказа.
- Повторная отправка на проверку.
- Возможность скрыть опубликованный товар.
- История модерации.

#### Административная панель

- Список продавцов.
- Список магазинов.
- Список товаров на проверке.
- Список жалоб.
- Блокировка продавца.
- Блокировка магазина.
- Скрытие товара.
- Управление категориями.

### 6.3. Что не обязательно включать в первый MVP

- Полноценная корзина.
- Онлайн-оплата.
- Автоматическая доставка.
- Сложная система комиссий.
- Полная кастомизация дизайна.
- Мобильные приложения.
- Сложный AI-ассистент.
- Автоматическое продвижение.
- Международные продажи.

Эти функции нужно предусмотреть в архитектуре, но не обязательно реализовывать сразу.

## 8. Субдомены

### 8.1. Основной формат

Использовать субдомены собственного домена:

- cups.allstore.am
- models.allstore.am
- handmade.allstore.am

Не покупать отдельный домен для каждого продавца.

### 8.2. Правила субдомена

- Субдомен должен быть уникальным.
- Запрещённые слова должны быть зарезервированы.
- Необходимо проверять формат и длину.
- Нельзя использовать чужие торговые марки без разрешения.
- Нужно предусмотреть защиту от оскорбительных или мошеннических названий.
- При смене субдомена старый адрес желательно перенаправлять на новый.
- Изменение субдомена может быть ограничено тарифом или платной услугой.

### 8.3. Техническая реализация

Рассмотреть:

- Wildcard DNS для *.allstore.am.
- Reverse proxy.
- Определение магазина по Host header.
- Проверку существования и статуса магазина.
- TLS/HTTPS для субдоменов.
- Кэширование публичных страниц.
- Защиту от подмены Host header.

### 8.4. Адреса товара и магазина

**Решено 2026-09-21.** Общий домен рекламирует магазины, товар принадлежит магазину.

- Магазин живёт по своему субдомену: `cups.allstore.am`. Это его канонический адрес.
- Товар живёт внутри магазина: `cups.allstore.am/p/{id}`. Это его канонический адрес.
- Общий домен несёт каталог, поиск, список магазинов и главную — то есть рекламу магазинов, а не сами товары.
- Адреса `allstore.am/p/{id}` и `allstore.am/s/{субдомен}` остаются рабочими и отвечают постоянным редиректом (308) на субдомен: ссылка, отправленная кому-то однажды, не должна ломаться.
- Клик по товару или по продавцу в каталоге уводит покупателя на субдомен магазина.

Следствие, принятое сознательно: поисковый вес распределяется по субдоменам, а не копится на общем домене. Взамен каждый магазин выглядит и индексируется как самостоятельный сайт, что соответствует обещанию «свой адрес» из раздела 2.

## 9. Multi-tenant архитектура

### 9.1. Общая модель

Одна кодовая база обслуживает множество магазинов.

Каждая сущность, относящаяся к магазину, должна быть связана с tenant/business ID.

Пример:

- businesses
- stores
- products
- product_images
- categories
- moderation_reviews

### 9.2. Основное правило безопасности

Каждый запрос к данным магазина должен проверять принадлежность данных соответствующему business_id.

Нельзя полагаться только на frontend-фильтрацию.

Проверки должны выполняться на backend-уровне.

### 9.3. Возможные модели multi-tenancy

Для MVP рассмотреть:

1. Общая база данных и общие таблицы с business_id.
2. Отдельная база данных для каждого магазина.
3. Отдельная схема базы данных для каждого магазина.

Для начальной версии вероятнее всего проще поддерживать общую базу с business_id, но окончательное решение принять после анализа требований безопасности, изоляции и масштабирования.

## 11. Модерация и безопасность

### 11.1. Модерация товаров

Рекомендуемый процесс:

1. Продавец создаёт товар.
2. Товар получает статус pending.
3. Товар не отображается публично.
4. Модератор проверяет содержание.
5. Модератор одобряет или отклоняет товар.
6. Одобренный товар публикуется.
7. При жалобе товар может быть повторно проверен.

### 11.2. Проверки

Проверять:

- Название товара.
- Описание.
- Фотографии.
- Категорию.
- Цену.
- Запрещённые товары.
- Возможные нарушения авторских прав.
- Ложную или вводящую в заблуждение информацию.
- Контактные данные.
- Соответствие правилам платформы.

### 11.3. Блокировка

Предусмотреть уровни:

- Скрытие отдельного товара.
- Приостановка магазина.
- Блокировка аккаунта.
- Полное удаление доступа.
- Повторная проверка после апелляции, если такая процедура будет принята.

Бан должен быть технически реализован как изменение статуса, а не как физическое удаление всех данных.

## 13. AI-ассистент

### 13.1. Цель

Помочь покупателю найти подходящие товары и магазины через обычный язык.

Пример:

Пользователь:

> Есть керамические чаши до 5000 драм?

Система:

1. Определяет категорию.
2. Определяет бюджет.
3. Ищет опубликованные товары.
4. Проверяет наличие.
5. Показывает карточки товаров.
6. Показывает магазины и ссылки.

### 13.2. Принцип достоверности

AI не должен самостоятельно придумывать:

- Наличие товара.
- Цену.
- Характеристики.
- Информацию о продавце.
- Условия доставки.

Ответ должен строиться на данных из базы AllStore.

### 13.3. Этапы внедрения

#### Этап 1

- Обычный поиск по названию и категории.
- Фильтры по цене и наличию.

#### Этап 2

- Семантический поиск.
- Распознавание естественных запросов.
- Поиск по описаниям товаров.

#### Этап 3

- AI-ассистент с инструментами поиска.
- Структурированные результаты.
- Уточняющие вопросы.
- Рекомендации на основе запроса.

#### Этап 4

- Персональные рекомендации.
- Сравнение товаров.
- Мультиязычная поддержка.
- Аналитика запросов.

## 14. Монетизация

Окончательная модель пока не выбрана. Архитектура должна позволять добавлять несколько источников дохода.

### Возможные источники

1. Ежемесячная подписка.
2. Платная кастомизация магазина.
3. Платное изменение субдомена.

На первом этапе рекомендуется сделать адаптивный веб-сайт или PWA, а отдельные приложения разработать после проверки востребованности.

**Решено 2026-09-19 (обновлено 2026-09-21):** веб (Next.js) реализуется первым — легче для поверхностного показа MVP. Мобильные приложения — следующий шаг: iOS решено делать на нативном Swift. Android — решение отложено: либо отдельный нативный Kotlin-проект (два раздельных кодовых базы, дороже в поддержке), либо кроссплатформенное решение (React Native/Flutter/Kotlin Multiplatform); принимается ближе к моменту реализации, не блокирует текущий MVP.

Backend спроектирован клиенто-независимым (`AllStore_build_plan.md`, раздел 4): один и тот же API обслуживает веб, iOS и будущий Android без переделки backend. Оба условия, которые мобильные клиенты предъявляют к backend заранее, уже выполнены: дуальная auth-схема принята и реализована (access + refresh с ротацией, ADR 1), API версионировано с первого дня (`/api/v1/...`). Перед стартом iOS-клиента остаётся одна правка — отдавать пару токенов не только в cookie, но и в теле ответа логина: cookie-jar у мобильного приложения нет. Версионирование здесь не формальность: мобильные приложения обновляются медленнее веба (через App Store/Google Play review), и несовместимое изменение контракта без версии сломает установленные версии у части пользователей.

## 23. Критерии готовности MVP

MVP можно считать готовым к тестированию, если:

- Пользователь может зарегистрироваться.
- Продавец может пройти процесс проверки.
- Продавец может создать магазин.
- Магазин получает уникальный субдомен.
- Продавец может добавить товар.
- Товар проходит модерацию.
- Одобренный товар отображается в магазине.
- Товар отображается в общем каталоге.
- Данные разных магазинов изолированы.
- Заблокированный магазин недоступен публично.
- Администратор может управлять товарами и продавцами.
- Основные сценарии покрыты тестами.
- Проект развёрнут в тестовой среде.
- Настроено резервное копирование базы данных.
- Существует базовая документация.

## 27. Итоговое видение

AllStore.am — это локальная платформа для Армении, которая объединяет:

- Онлайн-витрины небольших бизнесов.
- Общий каталог товаров.
- Субдомены под единым доменом.
- Модерацию и контроль качества.
- Продвижение продавцов через собственные каналы.
- Возможный AI-поиск товаров.
- Будущие заказы, оплату и мобильные приложения.

Первая версия должна быть простой, безопасной и пригодной для тестирования на реальных продавцах.

Главный технический принцип:

> Одна общая платформа, много независимых магазинов, изолированные данные и постепенное расширение возможностей.
