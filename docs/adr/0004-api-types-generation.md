# 0004. Типы frontend из OpenAPI: openapi-typescript с проверкой в CI

Статус: accepted
Дата: 2026-09-19

## Контекст

Принцип 5 плана сборки: один источник правды для контрактов — схемы Pydantic → OpenAPI →
типы frontend. Руками типы не дублируются. Нужен механизм, который не даёт им разойтись
незаметно.

## Решение

Генератор — `openapi-typescript`, только типы. Результат коммитится
(`frontend/src/lib/api-types.ts`), чтобы типы были видны в ревью и работали без запуска
backend.

Клиент запросов пишем сами поверх `src/lib/api.ts` — обёртка уже есть и в ней живёт
разделение серверного и браузерного base URL.

Проверка расхождения — шаг в `backend-ci`: там уже есть и Python, и node на раннере.
Шаг экспортирует схему из приложения, перегенерирует типы и падает, если результат
отличается от закоммиченного. Логика проверки лежит в backend-ci потому, что схема
меняется вместе с backend-кодом, и падать должен именно тот PR, который её сменил.

## Альтернативы

- **orval / hey-api.** Генерируют ещё и функции запросов с хуками react-query. Экономят
  код, но кладут в diff сотни сгенерированных строк и навязывают клиентскую библиотеку,
  которой пока нет в проекте.
- **Генерация на лету при сборке.** Нет артефакта в ревью, и frontend перестаёт собираться
  без поднятого backend.

## Последствия

- Изменение схемы Pydantic требует перегенерации типов в том же PR — иначе CI красный.
- Нужен способ отдать OpenAPI без поднятия сервера — небольшая команда экспорта в backend.
- Зависимость `openapi-typescript` в devDependencies frontend.
