# AllStore.am — RAG / AI Search Concept

## 1. Цель

AllStore.am — marketplace, который объединяет товары разных магазинов.

Покупатель не должен заранее знать, в каком магазине находится нужный товар. Он может:

* искать по названию;
* искать по URL товара;
* искать по SKU / коду товара;
* задавать естественный вопрос AI-помощнику.

Например:

> «Мне нужна небольшая белая ваза для гостиной»

Система должна понять запрос, найти подходящие реальные товары и показать покупателю результаты.

---

# 2. Что такое RAG

RAG = Retrieval-Augmented Generation.

В контексте AllStore RAG нужен для поиска релевантных товаров по смыслу запроса.

Главная идея:

```text
Запрос пользователя
        ↓
Поиск релевантных товаров
        ↓
Передача найденных товаров AI
        ↓
Формирование ответа
```

RAG не является заменой основной базы товаров.

PostgreSQL остаётся источником истины для:

* товаров;
* магазинов;
* цены;
* наличия;
* SKU;
* URL;
* категорий;
* характеристик.

RAG/Search Service отвечает именно за retrieval/search.

---

# 3. Основные компоненты

```text
Frontend
   ↓
Backend
   ├──────────────→ PostgreSQL
   │
   └──────────────→ AI Agent
                         ↓
                   RAG / Search Service
                         ↓
                  Vector Database
                         ↑
                  Embedding Model
```

### Backend

Основной API системы.

Он принимает запрос пользователя и решает, какой тип поиска нужен.

### AI Agent

Отвечает за:

* понимание диалога;
* понимание намерения пользователя;
* извлечение требований;
* уточняющие вопросы;
* формирование ответа пользователю.

### RAG / Search Service

Отвечает за поиск подходящих товаров.

### Embedding Model

Преобразует текст в числовой вектор.

```text
"белая ваза для гостиной"
        ↓
Embedding Model
        ↓
[0.12, -0.43, 0.81, ...]
```

### Vector Database

Хранит embeddings товаров и позволяет искать похожие по смыслу векторы.

---

# 4. Как создаётся embedding товара

Когда продавец добавляет или изменяет товар, его информация может быть преобразована в поисковый текст.

Например:

```text
Название:
Стеклянная ваза

Описание:
Небольшая прозрачная ваза для цветов.

Категория:
Дом и интерьер

Характеристики:
Высота 20 см
Материал: стекло
Цвет: прозрачный
```

Затем:

```text
Product data
    ↓
Search text
    ↓
Embedding Model
    ↓
Product embedding
    ↓
Vector Database
```

Embedding создаётся при добавлении или обновлении товара, а не при каждом поисковом запросе.

Если описание или другие важные данные товара изменились, embedding необходимо обновить.

---

# 5. Как работает поиск

Покупатель вводит:

> «Мне нужна небольшая ваза для цветов»

Для семантического поиска запрос также превращается в embedding:

```text
Запрос пользователя
        ↓
Embedding Model
        ↓
Query Vector
        ↓
Vector Search
        ↓
похожие Product Vectors
        ↓
Product IDs
```

После этого система получает реальные товары из основной базы.

---

# 6. Почему нужен semantic search

Обычный поиск может зависеть от совпадения слов.

Например:

```text
Запрос:
"сосуд для букета"

Товар:
"стеклянная ваза для цветов"
```

Слова не совпадают полностью, но смысл похож.

Semantic search с embeddings позволяет искать товары по смыслу, а не только по точному совпадению слов.

---

# 7. RAG не обязательно возвращает все совпадения

Обычно vector search возвращает наиболее релевантные результаты — например top-K.

```text
100000 товаров
      ↓
Vector Search
      ↓
Top 10 / Top 20 релевантных товаров
```

Если бизнес-требование — показать абсолютно все товары, соответствующие определённым условиям, это должно решаться поисковой/фильтрационной логикой, а не только RAG.

---

# 8. Exact Search и AI Search

Не каждый запрос нужно отправлять в AI/RAG.

Например:

```text
SKU-12345
```

Лучше искать напрямую:

```text
Backend
   ↓
PostgreSQL
   ↓
Exact product
```

То же самое относится к точному URL и другим структурированным идентификаторам.

Для естественного запроса:

```text
"Нужны чёрные кроссовки для бега до 50 000 драм"
```

можно использовать AI + RAG/Search.

Это важно и для скорости, и для предсказуемости.

---

# 9. Кто запускает RAG

RAG/Search Service работает как отдельный сервис, но он не начинает поиск сам по себе.

Backend решает, когда нужно обратиться к нему.

```text
Покупатель
    ↓
Frontend
    ↓
Backend
    ├── Exact Search ──────→ PostgreSQL
    │
    └── AI/Semantic Search → RAG/Search Service
                                  ↓
                              Vector DB
```

То есть:

> Backend отправляет запрос в RAG/Search Service, когда это необходимо.

---

# 10. Полный AI-поиск

Пример:

Покупатель:

> «Мне нужна небольшая белая ваза для гостиной»

Процесс:

```text
Buyer
  ↓
Frontend
  ↓
Backend
  ↓
AI Agent
  ↓
RAG / Search Service
  ↓
Query Embedding
  ↓
Vector Database
  ↓
Relevant Product IDs
  ↓
Backend
  ↓
Real Product Data
  ↓
AI Agent
  ↓
Answer to Buyer
```

Важно:

> AI не должен придумывать товары.

AI получает реальные найденные данные и использует их для формирования ответа.

---

# 11. Seller → Product → Embedding

Когда продавец добавляет товар:

```text
Seller
   ↓
Backend
   ↓
PostgreSQL
   │
   └────→ RAG / Search Service
                 ↓
          Embedding Model
                 ↓
          Vector Database
```

После этого товар доступен для semantic search.

---

# 12. Где находятся данные

Важно разделять:

### PostgreSQL

Источник истины:

```text
Products
Stores
Prices
Availability
SKU
URLs
Categories
Attributes
```

### Vector Database

Дополнительный поисковый индекс:

```text
Product ID
Embedding
Metadata
```

Embedding не заменяет сам товар.

Они связаны через Product ID:

```text
PostgreSQL
    │
    │ Product ID = 123
    │
    ├── name
    ├── description
    ├── price
    ├── stock
    └── seller


Vector DB
    │
    │ Product ID = 123
    └── embedding
```

---

# 13. Embedding — это дополнительный индекс

```text
Product
   │
   ├── обычные данные → PostgreSQL
   │
   └── embedding ─────→ Vector DB
```

Embedding нужен для поиска по смыслу.

Он не является заменой:

* названию;
* описанию;
* цене;
* SKU;
* наличию;
* магазину.

---

# 14. Что можно использовать для embedding

Для первой версии достаточно текстовых embeddings.

В embedding можно включать:

* название;
* описание;
* категорию;
* характеристики;
* важные атрибуты.

Например:

```text
"Apple iPhone 17,
смартфон,
256 GB,
чёрный,
OLED,
5G"
```

→ embedding.

Изображения и multimodal embeddings можно добавить позже.

---

# 15. Изменение товара

Если продавец изменил важные данные товара:

```text
Product updated
      ↓
Generate new embedding
      ↓
Update vector in Vector DB
```

Embedding должен соответствовать актуальным данным товара.

---

# 16. RAG/Search Service — его ответственность

Концептуально сервис отвечает за:

* создание embeddings для каталога;
* обновление embeddings;
* semantic search;
* поиск релевантных Product IDs;
* работу с Vector Database.

Он не должен становиться главным источником данных о товарах.

---

# 17. AI Agent — его ответственность

AI Agent отвечает за:

* понимание естественного языка;
* ведение диалога;
* определение требований пользователя;
* уточняющие вопросы;
* вызов поиска;
* формирование ответа.

Например:

```text
User:
"Хочу телефон для игр, но не очень большой"

AI Agent:
понимает требования

       ↓

RAG/Search:
находит подходящие товары

       ↓

AI Agent:
формирует ответ
```

---

# 18. Главное разделение системы

Для AllStore важно держать в голове три разные роли:

```text
┌─────────────────────┐
│      Backend        │
│                     │
│ API + бизнес-логика │
│ + источник данных   │
└──────────┬──────────┘
           │
     ┌─────┴─────┐
     ↓           ↓
┌─────────┐  ┌─────────────┐
│Postgres │  │ AI Agent    │
└─────────┘  └──────┬──────┘
                    ↓
             ┌──────────────┐
             │ RAG / Search │
             └──────┬───────┘
                    ↓
             ┌──────────────┐
             │ Vector DB    │
             └──────────────┘
```

### Backend

Хранение и бизнес-логика.

### AI Agent

Понимание пользователя и диалог.

### RAG/Search

Поиск нужных товаров.

# 19. Главный принцип для имплементации

Не нужно делать:

```text
User
 ↓
LLM
 ↓
LLM решает всё
```

Лучше:

```text
User
 ↓
Backend
 ↓
AI Agent
 ↓
Search/RAG
 ↓
Real Product Data
 ↓
AI Agent
 ↓
User
```

AI должен работать с реальными данными каталога.

# 20. Первая концептуальная версия AllStore Search

Поиск можно разделить на несколько уровней:

```text
                    User Query
                        │
                        ▼
                     Backend
                        │
              ┌─────────┴─────────┐
              │                   │
       Exact / Structured      AI / Semantic
              │                   │
              ▼                   ▼
         PostgreSQL          AI Agent
                                  │
                                  ▼
                            RAG / Search
                                  │
                                  ▼
                              Vector DB
                                  │
                                  ▼
                            Product IDs
                                  │
                                  ▼
                             PostgreSQL
                                  │
                                  ▼
                           Real Products
```

Это позволяет одновременно иметь:

* быстрый exact search;
* semantic search;
* AI shopping assistant;
* реальные данные о товарах;
* возможность масштабировать поиск отдельно от основного Backend.

---

# 21. Важное замечание о скорости

Поскольку AllStore должен быстро отвечать пользователю:

* exact-запросы не нужно отправлять через LLM;
* embeddings товаров создаются заранее;
* vector search выполняется отдельно;
* AI вызывается там, где действительно нужен естественный язык;
* PostgreSQL остаётся источником актуальных данных.

Идея:

```text
Простой запрос → максимально короткий путь

Сложный AI-запрос → AI Agent + RAG
```

---

# 22. Что пока НЕ нужно решать

На этапе концепции не обязательно сразу выбирать:

* конкретную LLM;
* конкретную embedding model;
* конкретную Vector DB;
* размер embedding;
* chunking strategy;
* similarity algorithm;
* инфраструктуру;
* Kubernetes;
* конкретные API.

Сначала нужно зафиксировать правильное разделение ответственности:

```text
Backend
   ↓
AI Agent
   ↓
RAG/Search
   ↓
Vector DB

и

Backend
   ↓
PostgreSQL
```

После этого можно переходить к выбору конкретных технологий.

---

# 23. Когда включать RAG (условие по объёму, не по дате)

Semantic search бесполезен на маленьком каталоге: на 30-50 товарах (объём первых 5-10 продавцов из Этапа 9 продуктового плана) обычный фильтр по категории справится не хуже, а сложность и стоимость появятся сразу.

Правило:

```text
RAG/Semantic Search включается не по календарному плану,
а по объёму активного каталога.

Пороговое значение — определить отдельно,
но ориентир: несколько сотен опубликованных товаров.
```

До этого порога:

* Exact/Structured Search (название, продавец, SKU, URL) — работает всегда, это часть базового MVP, не зависит от объёма.
* AI Agent и Vector DB — не разворачиваются, пока порог не достигнут.

---

# 24. Vector DB для MVP-масштаба: pgvector, а не отдельная система

На объёме MVP (тысячи, не миллионы товаров) отдельная vector-БД (Milvus/Qdrant/Weaviate) — избыточная инфраструктура: новый компонент, новый деплой, новый бэкап, новая точка отказа.

Решение по умолчанию для первой версии:

```text
PostgreSQL + расширение pgvector

Product ID остаётся общим ключом между
обычными данными товара и его embedding —
разделение из раздела 12 сохраняется,
просто оба живут в одной СУБД.
```

Отдельная vector-БД рассматривается только если `pgvector` реально упрётся в производительность на выросшем каталоге — не раньше и не "про запас".

---

# 25. Embedding pipeline — асинхронно, не в момент сохранения товара

Создание/обновление embedding не должно блокировать ответ продавцу при сохранении товара.

```text
Продавец сохраняет товар
        ↓
Backend отвечает 200 сразу
        ↓ (фоново)
Фоновая задача создаёт/обновляет embedding
        ↓
Vector DB (pgvector) обновлена
```

Для MVP достаточно простой background task (FastAPI `BackgroundTasks` или аналог); очередь (Redis + Celery/RQ) — когда объём потребует. Это тот же общий воркер-пул, что обслуживает уведомления (раздел 16 продуктового плана / Этап 8 build_plan) — не отдельная инфраструктура под embeddings.

---

# 26. AI Agent через tool use, а не самописный оркестратор

Вместо ручной логики "понял намерение → решил вызвать RAG → сформировал ответ" — использовать встроенный tool use / function calling современных LLM (включая Claude).

```text
LLM получает два инструмента:
  - exact_search(query)
  - semantic_search(query)

LLM сама решает, когда какой вызвать —
ровно по логике разделов 8-9 этого документа,
но без самописного orchestration-слоя.
```

Это меньше кода, меньше мест для ошибок, и совпадает с тем, что LLM для этого и проектировались.

---

# 27. Многоязычность запроса — без отдельного этапа перевода

Продуктовый план фиксирует один язык каталога (русский) на MVP. Если покупатель пишет на другом языке (например, армянском), отдельный шаг машинного перевода не нужен — многоязычная embedding-модель (например, семейство `e5-multilingual` или `bge-m3`) понимает смысл запроса на разных языках напрямую, без промежуточного перевода как отдельного компонента.

---

# Краткое резюме

RAG в AllStore — это слой поиска по смыслу.

Он не заменяет PostgreSQL и не является самим AI Agent.

```text
PostgreSQL
= реальные данные товаров

Vector DB
= embeddings для semantic search

RAG/Search
= поиск релевантных товаров

AI Agent
= понимание пользователя + диалог

Backend
= связывает всё вместе и управляет запросами
```

Главная идея:

> Backend сам решает, когда отправлять запрос в RAG/Search Service. RAG/Search Service работает как отдельный сервис, а Vector DB хранит поисковые embeddings товаров.

RAG включается по объёму каталога, а не по дате; для MVP-масштаба Vector DB = pgvector внутри существующего PostgreSQL, без отдельной системы. RAG/Search — единственный компонент AllStore, вынесенный в отдельный сервис (см. `AllStore_build_plan.md`, ADR 10): другой профиль нагрузки, другой стек, полная опциональность для работы сайта.
