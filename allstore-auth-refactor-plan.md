# AllStore: план рефакторинга аутентификации

Основан на `allstore-auth.md` (карта текущей системы) и принятых решениях. Цель: убрать классы ошибок в аутентификации, а не «залатать баги». Безопасность без багов недостижима, достижимо сузить поверхность атаки и закрыть критичное тестами и внешним пентестом.

## 1. Принятые решения

| # | Решение |
|---|---|
| D1 | Покупатели и продавцы: регистрация и вход **паролем или через Google**. |
| D2 | Модераторы и админ: **первый вход только email + пароль** (выдаётся при создании, `must_change_password`). Вход через Google появляется **только после** привязки из уже авторизованной сессии. |
| D3 | Сессия привязывается к устройству: запись устройства + ключ устройства для refresh. |
| D4 | Google OIDC (code + PKCE), идентичность по `sub`, не по email. |
| D5 | Рекомендация: перейти с JWT+refresh на **непрозрачные серверные сессии** (ADR 0001 пересматривается). Если оставляем JWT, фазы 3 и 4 делаются поверх `sessions` всё равно. |

### Уточнения к D2 (важно)

- «Захардкоженный» пароль не должен лежать в коде или репозитории. Источник: переменная окружения / секрет деплоя (`ADMIN_BOOTSTRAP_PASSWORD`), используется один раз, при первом создании. Пароль в git = скомпрометирован навсегда.
- Для модераторов пароль генерируется случайно при создании админом (как сейчас), а не общий.
- Временный пароль: срок жизни 24–72 часа, `must_change_password=true`, нигде не логируется.
- Привязка Google для staff: только из авторизованной сессии, после повторного ввода пароля (step-up), с проверкой `email_verified` и совпадения email с адресом аккаунта. Автоматического слияния по email нет.
- После привязки Google вход паролем для staff **не отключается автоматически** (break-glass), но на staff включается TOTP/WebAuthn (Фаза 7). Решение о запрете пароля после привязки принять отдельно.
- Админ по-прежнему один (`uq_users_single_admin`), Google не меняет эту гарантию.

## 2. Принципы

1. Один вход в систему: `get_current_user` остаётся единственной дверью. Google, пароль и будущее проходят через одни `authenticate` → `_ensure_active` → `issue_session`.
2. Статус пользователя перечитывается на каждый запрос (бан мгновенный).
3. Никаких различий в ответах и по времени, которые позволяют перечислять аккаунты.
4. Всё, что меняет безопасность аккаунта, требует свежего подтверждения (пароль / step-up) и порождает письмо-уведомление.
5. Тесты проверяют реальный жизненный цикл (сессия БД, коммит, новая сессия), а не подменённые фикстуры.

## 3. Фазы

### Фаза 0. Починка критичного и тестовой инфраструктуры (до всего остального)

- [ ] **Кража refresh-токена не сохраняется** (`services/auth.py:152`, `api/auth.py:92`). Отзыв семьи выполнять в отдельной транзакции, коммитящейся до `raise`; либо возвращать результат `reuse_detected`, эндпоинт коммитит и затем отдаёт 401.
- [ ] Переписать `test_auth_session.py:72`: без подмены `get_session` на общий объект; проверка из **новой** сессии, что семья отозвана и данные персистятся.
- [ ] Общее правило для остальных тестов: интеграционные тесты auth используют реальный жизненный цикл `get_session`.
- [ ] Закрыть п.7: `path.endswith(tuple)` в `deps/auth.py:54` заменить на точное сравнение или явный `Depends(allow_during_password_change)` на трёх роутах.

**Готово, когда:** тест воспроизводит проблему на старом коде (красный), на новом зелёный.

### Фаза 1. Rate limiting и защита от DoS

- [ ] Лимиты: login (по IP и отдельно по email), register, password-reset request/confirm, refresh, Google callback, смена пароля/email, moderator password routes.
- [ ] Нарастающая задержка вместо жёсткого локаута (чтобы чужими попытками нельзя было заблокировать аккаунт).
- [ ] Использовать `TooManyRequestsError` (`core/errors.py:61`), ответ 429 с `Retry-After`.
- [ ] Хранилище счётчиков: Redis (или аналог), не память процесса.
- [ ] argon2 выносить в threadpool с семафором, ограничивающим параллелизм.
- [ ] Метрики и алерты на всплески 429 и неудачных входов.

### Фаза 2. Куки, CSRF, заголовки

- [ ] Куки host-only, без `Domain=.allstore.am`; префиксы `__Host-` / `__Secure-`; `SameSite=Lax` явно; `Secure` везде кроме local.
- [ ] Основная сессия не уходит на витрины продавцов на сабдоменах (иначе XSS/захват сабдомена = доступ к API; плюс cookie tossing ломает double-submit). **Проверить, зависит ли что-то от общей сессии между сабдоменами**; если да, отдельная схема (SSO-handoff или отдельный origin для кабинета).
- [ ] CSRF: токен привязан к сессии (HMAC), проверка `Origin` и `Sec-Fetch-Site` в дополнение к `X-CSRF-Token`.
- [ ] Заголовки: CSP (строгий, с nonce), HSTS, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer` на страницах с токенами, `X-Content-Type-Options`.
- [ ] Обновить фронтенд (`browser-api.ts`, `dal.ts`, `proxy.ts`) под новые имена кук.

### Фаза 3. Модель сессий и устройств

Рекомендуемая схема (D5), таблица `sessions`:

| поле | назначение |
|---|---|
| `id` | идентификатор сессии |
| `user_id` | владелец |
| `family_id` | устройство/семья токенов |
| `token_hash` | sha256 текущего непрозрачного токена |
| `device_public_key` | публичный ключ устройства (Фаза 4), nullable до внедрения |
| `user_agent`, `ip`, `asn`, `country` | сигналы риска (не жёсткая привязка) |
| `auth_method` | `password` / `google` |
| `created_at`, `last_seen_at` | аудит и список устройств |
| `idle_expires_at`, `absolute_expires_at` | скользящий и абсолютный срок |
| `revoked_at`, `revoked_reason` | отзыв |

- [ ] Миграция, `issue_session` вместо `issue_tokens`.
- [ ] Отзыв **одной** семьи (устройства) вместо всех токенов пользователя; «выйти на этом устройстве» и «выйти везде».
- [ ] Ротация с коротким окном допуска (10–30 с) и single-flight на клиенте, чтобы несколько вкладок не выглядели как кража.
- [ ] Повторное использование отозванного токена вне окна: отзыв семьи + запись в аудит + письмо (с учётом исправления из Фазы 0).
- [ ] Бан/блокировка отзывает все сессии пользователя (как сейчас с refresh).
- [ ] Закрывает пп.2 и 6 исходного списка (мёртвый refresh, неиспользуемый `role`). Если остаётся JWT: подключить 401-retry в `browser-api.send` и `dal.backendGet`, `role` либо использовать, либо не выдавать; `algorithms=["HS256"]` явно, проверка `iss`/`aud`, `kid`, секрет ≥ 32 байт.
- [ ] Эндпоинт и страница «Мои устройства».
- [ ] Страницы, чтобы выживать 401 на SSR (`dal.ts`) без петли на `/login`.

### Фаза 4. Привязка к устройству

Слои:

1. **Запись устройства** (Фаза 3): UA, ASN, страна, `last_seen_at`.
2. **Сигналы риска, не жёсткая привязка к IP/UA:** смена страны или ASN даёт step-up (повторный пароль) и письмо «новый вход». UA и IP не привязывать жёстко: IP меняется, UA крадётся вместе с кукой.
3. **Ключ устройства для refresh (DPoP-подобная схема, RFC 9449):**
   - [ ] Браузер генерирует через WebCrypto неизвлекаемую пару ключей (`extractable: false`, IndexedDB), публичный ключ регистрируется при входе в `sessions.device_public_key`.
   - [ ] `/auth/refresh` требует подписанный proof (метод, URL, время, одноразовый `jti`); `jti` хранится для защиты от повтора.
   - [ ] Access/сессионная кука без подписи на каждый запрос (дорого и хрупко).
   - [ ] Не защищает от XSS (скрипт на странице может вызвать подпись): CSP из Фазы 2 обязателен.
   - [ ] Fallback для браузеров без поддержки: сессия без привязки, но с более коротким абсолютным сроком и сигналами риска.
4. **Chrome DBSC:** прогрессивное усиление; перед использованием проверить актуальный статус поддержки в документации (Chromium-only).
5. **Мобильные клиенты:** ключ в Keychain/Secure Enclave или Keystore, токены в защищённом хранилище, опционально App Attest / Play Integrity.
- [ ] Step-up (свежая аутентификация ≤ 5–10 мин) для опасных действий: смена email/пароля, привязка/отвязка Google, выплаты продавца, админские операции.

### Фаза 5. Email: подтверждение, смена, сброс пароля

- [ ] Реальная отправка писем (заменить stub `send_password_reset_email`), асинхронно через очередь, чтобы время ответа не выдавало существование аккаунта.
- [ ] **Подтверждение email при парольной регистрации** (закрывает pre-hijacking и делает безопасной привязку Google). До подтверждения доступ ограничен (определить, что именно недоступно).
- [ ] `email_verified_at` становится живым (п.5): пишется при подтверждении и при регистрации через Google (`email_verified=true`).
- [ ] Смена email: `pending_email`, письмо с подтверждением на **новый** адрес, уведомление на старый; пока не подтверждено, старый адрес действует.
- [ ] Сброс пароля: UI («забыли пароль» + страница подтверждения), токен 30–60 мин, новый запрос инвалидирует старые, одноразовый, `Referrer-Policy: no-referrer`, после сброса отзыв всех сессий.
- [ ] Регистрация без перечисления: при занятом email отвечать нейтрально («письмо отправлено»), на почту владельцу отправлять уведомление.
- [ ] Гонка при регистрации: полагаться на уникальный индекс по `lower(email)` (или `citext`) и ловить `IntegrityError`, а не на `ensure_identifiers_free`.
- [ ] Телефон: либо верификация, либо снять уникальность непроверенного номера (иначе можно «занять» чужой).
- [ ] Пароли: нормализация NFKC, проверка по утёкшим паролям (HIBP, k-anonymity), без правил состава; пересмотреть параметры argon2 (память выше минимума, если сервер позволяет).

### Фаза 6. Вход через Google (покупатели и продавцы)

**Модель данных**

```
user_identities
  id, user_id → users, provider ('google'), provider_sub (UNIQUE с provider),
  email_at_link, linked_at, last_login_at
users.password_hash → nullable
```

**Поток (buyer / seller)**

```
GET /auth/google/start?role=buyer|seller
  → сервер создаёт state + nonce + PKCE verifier, кладёт в короткоживущую
    httpOnly-куку (SameSite=Lax) / серверное хранилище, роль сохраняет на сервере
  → 302 на Google

GET /auth/google/callback?code&state
  → проверить state (привязан к браузеру), обменять code на токены на бэкенде (PKCE)
  → проверить ID-токен: подпись по JWKS, iss, aud=client_id, exp, nonce
  → требовать email_verified == true
  → по (google, sub):
       найден       → authenticate → _ensure_active → issue_session
       не найден:
         email занят парольным аккаунтом → НЕ сливать; предложить войти паролем
                                           и привязать Google из настроек
         email свободен → создать User(role из state) + identity,
                          email_verified_at = now, [seller] Business(pending)
```

- [ ] Scope только `openid email profile`; redirect URI с точным совпадением; без wildcard.
- [ ] Продавец через Google: после создания аккаунта обязательный шаг онбординга (legal_name, display_name, phone) до публикации бизнеса; Business остаётся `pending` до модерации.
- [ ] Роль только `buyer` или `seller`. Попытка создать moderator/admin через Google невозможна.
- [ ] Привязка/отвязка Google в настройках (step-up), нельзя отвязать последний способ входа; для Google-аккаунтов поток «задать пароль».
- [ ] Смена email у Google-аккаунта: запретить или подтверждать новый адрес.
- [ ] Rate limit и аудит на `/start` и `/callback`; ошибки Google не раскрывают детали пользователю.
- [ ] Мобильные клиенты: системный браузер (ASWebAuthenticationSession / Custom Tabs) + PKCE, без WebView.

### Фаза 7. Staff-аккаунты (модераторы и админ)

Реализует D2.

- [ ] Первый вход: email + пароль. Админ: bootstrap из секрета окружения (идемпотентный, с advisory lock, как сейчас, без перезаписи существующего пароля). Модератор: случайный временный пароль от админа.
- [ ] `must_change_password` обязателен; временный пароль истекает через 24–72 ч; пароли не попадают в логи.
- [ ] После смены пароля: привязка Google из настроек (step-up, `email_verified`, email совпадает с аккаунтом). Только после привязки в `/auth/google/start` разрешён вход для этих ролей, и только по уже существующей identity; **создание staff через Google невозможно**.
- [ ] Вход staff через Google: если identity для staff-аккаунта не привязана, ответ без раскрытия факта существования аккаунта.
- [ ] 2FA (TOTP или WebAuthn) для admin и moderator; step-up для опасных действий (бан, смена ролей, передача админа).
- [ ] Права действий остаются по рангам (`services/permissions.py`), скрытие целей через 404 сохраняется.
- [~] `scripts/grant_role.py` (break-glass): аудит есть — запись без актора, как у `bootstrap` (фаза 8). Запуск и так только с серверной оболочки. Алерт — вместе с остальной наблюдаемостью, которой нет.

### Фаза 8. Аудит, уведомления, наблюдаемость

- [x] Журнал событий безопасности — с одной поправкой, зафиксированной в [ADR 21](docs/adr/0021-security-journal-and-notices.md): успешный вход в журнал не дублируется (он уже записан в `sessions`, полнее), а неудачный уходит в лог, а не в неудаляемую таблицу, которую умеет наполнять аноним. Остальное на месте: повтор токена, привязка и отвязка Google, смена пароля и адреса, создание и сброс staff, смена ролей, бан, break-glass (`bootstrap` и `grant_role`).
- [x] Письма пользователю: новый вход с нового устройства (только когда аккаунт уже был открыт где-то ещё), смена пароля, смена адреса — старому адресу, привязка и отвязка Google.
- [ ] Алерты: всплески неудачных входов, reuse refresh, 429, любые действия break-glass. **Не сделано:** в репозитории нет ни сборщика логов, ни метрик, ни адресата алерта. Источник появился — строки лога и записи журнала; стека наблюдаемости нет.
- [x] Логи без токенов, паролей, кодов Google. Единственное исключение — стенд без почтового сервера пишет тело письма в лог, потому что ссылку оттуда и берут; вне `local` не пишет ([ADR 19](docs/adr/0019-transactional-mail.md)).

## 4. Порядок и зависимости

```
Фаза 0 ─┬─ Фаза 1 ─ Фаза 2 ─ Фаза 3 ─ Фаза 4
        │                      │
        └─ Фаза 5 (email) ─────┴─ Фаза 6 (Google) ─ Фаза 7 (staff) ─ Фаза 8 ─ Фаза 10
                                                                          Фаза 9 (после 3, 4, 6)
```

Жёсткие зависимости:

- Фаза 6 (Google) **не начинается** до Фазы 5 (подтверждение email) и Фазы 3 (`sessions`).
- Фаза 4 зависит от Фазы 3.
- Фаза 7 зависит от Фаз 3, 5, 6.
- Фаза 0 первая, без неё остальные тесты нельзя считать надёжными.

## 5. Негативные тесты (обязательный набор)

- Повтор отозванного refresh: семья отозвана и это видно из новой сессии.
- Два параллельных refresh одним токеном (окно допуска): не считается кражей; позже окна: считается.
- Украденная кука/refresh без ключа устройства не работает.
- Google callback: неверный `state`, неверный `nonce`, чужой `aud`, просроченный/подделанный ID-токен, `email_verified=false`, повтор `code`.
- Google: аккаунт с тем же email, что и парольный, не сливается.
- Через Google невозможно создать moderator/admin; staff без привязанной identity не входит.
- Привязка Google staff без step-up отклоняется; нельзя отвязать последний способ входа.
- Заблокированный/приостановленный пользователь не входит ни паролем, ни Google; бан отзывает сессии.
- Временный пароль staff после срока не работает; `must_change_password` не позволяет ничего, кроме смены пароля.
- Перечисление: одинаковые ответы и время для существующего/несуществующего email (login, register, reset).
- Rate limit срабатывает по IP и по email, 429 с `Retry-After`.
- CSRF: запрос без токена, с чужим токеном, с неверным `Origin` отклоняется.
- Cookie tossing: подмена CSRF-куки с сабдомена не проходит.
